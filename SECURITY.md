# Security reporting

Use [GitHub's private vulnerability reporting page](https://github.com/csshlok/Sentinel/security/advisories/new) to report a vulnerability. If that page is unavailable, [open a minimal issue](https://github.com/csshlok/Sentinel/issues/new) asking for a private contact channel. Do not include exploit steps, secrets, or affected repository contents in a public issue.

Please include the Sentinel version (`sentinel --version`), Windows version, affected feature, reproduction steps, and whether the issue requires a local user, a repository under agent control, or a hostile Passport bundle. Redact credentials and private repository data. Maintainers have not committed to a response time or a coordinated disclosure schedule.

## Threat model and current limits

Sentinel handles untrusted agent output, repository contents, Git metadata, and imported Passport bundles. It uses scoped authority checks, supervised processes, Git and journal evidence, and signed exports. Those controls have distinct limits:

- The built-in Claude profile attempts a verified Windows AppContainer launch. The generic profile uses a restricted token and Job Object; that profile does not isolate filesystem or network access. The built-in Codex profile currently refuses to launch. Passport v2 binds each launch's observed boundary and claims the weakest: `APPCONTAINER` only when the launch's workspace run recorded verified token facts (AppContainer token, Low integrity, Job Object verified before resume) for that workspace's package SID and the launch record matches them; `RESTRICTED_TOKEN` or `UNCONFINED` for weaker launches; `UNKNOWN` for attached runs or records that cannot establish a boundary. The claim describes the agent process at launch, not later descendants' file or network activity.
- A selected policy preset gates the `REVIEW_READY` and `PR_OPEN` transitions on a current `ALLOW`; a Change without a preset is not gated. Apply-back refuses a sealed diff that adds, changes, deletes or renames a Change Contract forbidden path, at preview and again at apply.
- A repository contract (`.sentinel/contract.toml`) is read only from the Change's baseline commit, as a regular committed file of at most 64 KiB, never from the working tree; an agent's edit to it takes effect only after a new baseline is captured. Whoever can commit to the repository before the baseline therefore decides the contract it loads.
- Software-provider signing keys are protected by Windows CNG export policy, but another process running as the same user may be able to extract them through DPAPI. A TPM provider offers a stronger hardware boundary when available. A valid signature proves integrity under the displayed key, not that the host or signer was uncompromised.
- Confined checks cover the Python toolchain (`python`, `python3`, `pytest`) and the Node toolchain (`node`, `npm`; `pnpm` and `yarn` are mapped the same way but are not yet exercised by a real-box test, and a `node_modules` built from links or junctions, as pnpm and npm workspaces build it, is refused with `CHECK_RUNTIME_UNSAFE_SOURCE`; a Yarn Plug'n'Play project has no `node_modules` snapshot and is refused too). Each check runs in a per-run AppContainer with no capabilities, over a copy of the repository's tracked and untracked files (an untracked file is excluded when the current ignore rules or the committed `.gitignore` files of the Change's baseline commit ignore it, so an agent's edit to `.gitignore` cannot bring a file such as `.env` into a check; a repository with untracked files and no baseline commit is refused), using read-only runtime snapshots granted to that box only. Real-boundary acceptance tests (`backend/tests/acceptance/test_confined_checks.py`), each with a host positive control, show an agent-authored `conftest.py`, `npm test` script or `postinstall` script run by `npm install --offline` cannot write outside the box, read the Sentinel store (API token, database, trust registry), read the user repository, read a Windows Credential Manager secret, open a per-user CNG signing key, connect to the local API or any other loopback port, or reach the internet. The box can still read what Windows grants every AppContainer (for example System32 and Program Files), and a check can consume CPU, memory and its scratch space until its timeout.
- What is not confined: `uv`, `cargo`, `go` and `dotnet` have no confined runtime. They are refused unless an actor holds a delegated `checks.unconfined` authority on a Change whose contract admits HIGH risk. Such a run executes as an ordinary child process at the user's authority in the user repository (with a reduced environment only), is journaled as `check.unconfined_run`, is listed with boundary `UNCONFINED`, and makes the Change's Passport `confined_checks` claim `FAIL`. Executables outside the allowlist are refused.
- Inside a confined check, a project's `node_modules` is reachable through `NODE_PATH` (CommonJS resolution) only, not ES module resolution; Node runs with `--preserve-symlinks` (the tree and snapshots contain no links). Editable installs, `.egg-link` files and `.pth` path entries that point outside the interpreter's site-packages are not available in the box and are reported as runtime limitations. `.pth` files inside site-packages (relative path entries and `import` lines) are processed in the box as in the venv, through a `sitecustomize` hook in Sentinel's interpreter snapshot; if the base interpreter ships its own `sitecustomize.py`, the hook is not added and every `.pth` file is reported as a limitation instead. Dependencies installed in the snapshot run inside the box, so a hostile dependency is confined, not prevented.
- Diff coverage measures executed changed Python lines. Execution does not prove assertion quality or correctness. Unknown mapping, freshness, or collection results must remain `UNKNOWN` or `STALE` and cannot satisfy a required rule.
- The diff-coverage caller monitor runs inside the test process, so code under test can tamper with it. A monitor that was disabled or replaced before the run ended makes the claim `UNKNOWN`, but code that turns it off and on again between calls, or starts a thread directly on a test function, is not attributed. Out-of-process evidence would be needed to close that.
- The `docs` preset inventory omits untracked files hidden by `.git/info/exclude` or `core.excludesFile`. Those local exclude rules are outside the bound checkpoints, so such files are invisible to a docs-only decision until explicitly staged with `git add -f`; a normal commit cannot include them while they remain ignored.
- The journal hash chain detects edits to recorded history, but a process with authority over the local database, key, and runtime can replace the whole evidence set. The operator must establish trust in a public-key fingerprint separately.
- Direct build, runtime and test dependencies are pinned in `pyproject.toml`; transitive dependencies are not locked and may resolve differently between installs.
- GitHub Check publication is bound to an observed PR head and policy revision at publication time. A later push or policy change makes earlier results stale; GitHub's presentation is not the source of evidence. Verify a downloaded `.sentinel` bundle independently with `sentinel verify`.
- The lesser commit statuses are unauthenticated. A repository writer can forge a `sentinel/passport/*` status; verify the exported `.sentinel` bundle against a fingerprint trusted independently of that status. On CI or non-Windows hosts, `python -m backend.app.passport.portable_verify BUNDLE --fingerprint FP` and the `.github/actions/verify-passport` composite Action do this with only `cryptography` and `pydantic` installed and no local trust registry: the pinned fingerprint is the sole trust root.
- For repositories whose `origin` is on gitlab.com, CI outcomes come from GitLab commit statuses read under a separate `gitlab.repo.read` grant; self-managed GitLab hosts are not supported. A commit status is only as trustworthy as the project members allowed to post statuses, and only finished states (success, failed, canceled, skipped) count as a conclusion.
- Real AppContainer tests depend on Windows facilities and a locally usable Node executable. GitHub-hosted Windows runners (a Server SKU) deny an AppContainer the NUL device and System32 spawns (which `npm` scripts need), and their toolcache Python install contains a reparse point that the check-runtime snapshot refuses by design. The real-boundary tests therefore skip on hosted runners unless `SENTINEL_CI_REAL_APPCONTAINER=1` is set; the boundary evidence comes from local Windows 11 runs, and confined checks on Windows Server have not been demonstrated. Hosted runners without a usable TPM exercise disposable software-provider test keys. Production signing still fails closed when the Platform provider reports `NTE_DEVICE_NOT_READY`, because that status might hide an existing TPM identity.

Do not use this pre-release software as the only control protecting valuable credentials or repositories.
